# 导航与页面架构说明

> 适用项目：RailWeldApp（WPF + .NET 10 + CommunityToolkit.Mvvm）  
> 本文说明五个机制各自的职责：**导航服务、页面工厂、页面生命周期、弱事件、消息总线**，以及当前项目为什么这样选。

---

## 0. 一句话版本

| 机制 | 解决什么问题 | 一句话 |
|---|---|---|
| 导航服务 | 当前显示哪个页面 | 持有 `CurrentView`，负责切换并通知界面 |
| 页面工厂 | 页面 VM 怎么创建 | 从 DI 解析 Transient VM，可带初始化回调 |
| 生命周期 | 进入/离开页面时做什么 | 加载数据、取消请求、释放页面级资源 |
| 弱事件 | 页面 VM 会不会被单例留住 | Transient VM 订阅单例事件时用弱引用，切页可回收 |
| 消息总线 | 模块之间怎么解耦通知 | 发“事件”，**不拿它做页面路由** |


- **管理台内部**：总览、实时、手动、自动等，由 `IAdminNavigationService` 负责。

## 2. 导航服务

### 2.1 职责

导航服务只做三件事：

1. 持有“当前页面”这个唯一状态（`CurrentView`）；
2. 创建并切换到目标页面；
3. 通过 `INotifyPropertyChanged` 通知界面刷新。

它不负责页面内部的数据加载、不负责页面 View 的创建（View 由 `DataTemplate` 创建）。

### 2.2 两个接口

`Interfaces/INavigationService.cs`：

```csharp
public interface INavigationService : INotifyPropertyChanged
{
    ViewModelBase? CurrentView { get; }

    void NavigateTo<TViewModel>(Action<TViewModel>? init = null)
        where TViewModel : ViewModelBase;
}
```

`Interfaces/IAdminNavigationService.cs` 结构相同，只是语义限定在管理台内部。

`CurrentView` 在接口上是**只读**的，外部不能直接赋值，必须走 `NavigateTo`，这样生命周期不会被绕过。

### 2.3 实现流程

`Services/NavigationService.cs` 和 `Services/AdminNavigationService.cs` 的核心逻辑一致：

```csharp
TViewModel next = pageFactory.GetViewModel(init);

if (ReferenceEquals(CurrentView, next))
    return;

NavigationLifecycle.Leave(CurrentView, logger);

CurrentView = next;

NavigationLifecycle.Enter(next, logger);
```

顺序很重要：

1. **Leave 旧页面**：让旧页面取消加载、停计时器；
2. **切 CurrentView**：界面收到通知，开始换页；
3. **Enter 新页面**：新页面开始加载。

### 2.4 为什么状态放在服务里

一个常见的疑问是：既然 `AdminViewModel` 已经能拿到当前页，为什么不让它直接持有 `CurrentPage`？

当前项目选择服务持有状态，原因是：

- **子页面要互跳**：总览页的“查看实时数据/温度监视”需要跳到兄弟页面。子页面不应该反向依赖 `AdminViewModel`；
- **统一入口**：以后加参数、未保存拦截、返回栈、导航日志，都只需要改导航服务；
- **可测试**：测试时可以替换 `IAdminNavigationService`，不用构造整个管理台外壳；
- **单一状态源**：`AdminViewModel.CurrentPage` 只是代理：

```csharp
public ViewModelBase? CurrentPage => _adminNavigationService.CurrentView;
```

它不保存第二份状态，所以不存在“服务里一个当前页、VM 里又一个当前页”的同步问题。

### 2.5 当前文件

- `Interfaces/INavigationService.cs`
- `Interfaces/IAdminNavigationService.cs`
- `Services/NavigationService.cs`
- `Services/AdminNavigationService.cs`
- `ViewModels/AdminViewModel.cs`（订阅管理台导航，刷新高亮）

## 3. 页面工厂（PageFactory）

### 3.1 职责

`PageFactory` 只负责**创建页面 VM**：

```csharp
public sealed class PageFactory(IServiceProvider provider)
{
    public T GetViewModel<T>(Action<T>? init = null) where T : ViewModelBase
    {
        T viewModel = provider.GetRequiredService<T>();

        init?.Invoke(viewModel);

        return viewModel;
    }
}
```

它解决两个问题：

- 页面 VM 有构造函数依赖时，业务代码不用手写 `new`；
- 页面需要在“成为 CurrentView 之前”设置参数，例如历史查询的焊缝编号。

使用示例：

```csharp
_adminNavigationService.NavigateTo<AdminHistoryQueryViewModel>(
    vm => vm.SearchWeldNo = weldNo);
```

`init` 在页面切换前执行，所以页面第一次显示时数据上下文已经就绪，不会先闪一下空页面。

### 3.2 为什么不让业务代码直接用 IServiceProvider

- `GetRequiredService<T>()` 散落在命令里，依赖关系不直观；
- 页面创建逻辑分散后，很难统一加日志、参数、缓存策略；
- `PageFactory` 把“创建页面”收敛到一个地方，导航服务只依赖它。

### 3.3 为什么不直接 new

- 页面 VM 后续会注入服务（PLC、数据库、对话框）；
- `new` 会绕开 DI 生命周期和测试替换；
- Transient 页面每次进入需要新实例，`PageFactory` 正好利用 DI 的 Transient 注册。

### 3.4 新增页面时的完整步骤

1. `ViewModels/AdminXxxViewModel.cs`：继承 `PageViewModel`；
2. `Views/AdminXxxView.xaml`：`UserControl`，根元素不写死宽高；
3. `Themes/ViewTemplates.xaml`：补一行 `DataTemplate`；
4. `ServiceCollectionExtensions`：注册 `AdminXxxViewModel` 为 `Transient`；
5. `Enum/PageName.cs`：加枚举值；
6. `AdminViewModel`：加导航命令和高亮属性；
7. `AdminView.xaml`：顶部导航加按钮；
8. 可选：实现 `INavigationAware`、使用 `SubscribeWeak`。

> 新增页面**不需要**再改页面工厂的 switch，也不需要注册 View。

## 4. 页面生命周期（INavigationAware）

### 4.1 接口

`Interfaces/INavigationAware.cs`：

```csharp
public interface INavigationAware
{
    void OnNavigatedTo();

    void OnNavigatedFrom();
}
```

页面 VM 可选实现。导航服务在切换时自动调用，调用点统一在 `Services/NavigationLifecycle.cs`。

### 4.2 调用顺序

```text
Leave(旧页面)
   ↓
CurrentView = 新页面
   ↓
Enter(新页面)
```

- `OnNavigatedFrom`：在 `CurrentView` 被替换**之前**调用，用于取消请求、停计时器；
- `OnNavigatedTo`：在 `CurrentView` 已经指向新页面**之后**调用，用于加载数据。

回调是**同步、UI 线程**的。异常会被 `NavigationLifecycle` 捕获并记日志，不会让页面切换崩溃。

### 4.3 一个带取消的页面示例

```csharp
public partial class AdminHistoryQueryViewModel : PageViewModel, INavigationAware
{
    private CancellationTokenSource? _cts;

    public void OnNavigatedTo()
    {
        _cts = new CancellationTokenSource();
        _ = LoadAsync(_cts.Token);
    }

    public void OnNavigatedFrom()
    {
        _cts?.Cancel();
        _cts?.Dispose();
        _cts = null;
    }

    private async Task LoadAsync(CancellationToken cancellationToken)
    {
        // 查询数据库 / 请求接口
    }
}
```

原则：

- 生命周期方法里**不要阻塞**等 I/O；
- 异步加载自己启动任务，并保存 `CancellationTokenSource`；
- 离开页面时取消，避免旧页面的请求回来更新已经不在的界面。

### 4.4 为什么不写成 async 生命周期

如果把接口写成 `Task OnNavigatedToAsync()`，导航方法也必须变成 `NavigateToAsync`，所有导航命令都要改成异步命令；在页面加载失败时还要处理异常和“加载中”状态。

当前项目页面还很简单，先用同步生命周期 + 页面内部异步加载，成本最低。  
以后确实需要“加载完再显示页面”时，再加 `NavigateToAsync`，接口可以并存。

### 4.5 当前使用

- `AdminViewModel` 实现 `INavigationAware`：
  - `OnNavigatedTo`：收起通知抽屉，并回到总览；
  - `OnNavigatedFrom`：离开管理台时收起抽屉。
- 这样即使 `AdminViewModel` 是单例，注销再登录也不会停在上次页面。

## 5. 弱事件（WeakEventManager）

### 5.1 要解决的问题

页面 VM 是 `Transient`，每次导航都会新建。  
如果页面 VM 里这样订阅单例：

```csharp
_plcDataCache.PropertyChanged += OnPlcDataChanged;
```

`PlcDataCache` 是单例，它的 `PropertyChanged` 事件会**强引用**页面 VM。  
页面离开后，View 和 DataContext 虽然断开了，但缓存仍然抓着旧 VM：

- 旧 VM 无法 GC；
- 每次进页面都会多一个订阅者；
- 切换越多，内存和回调越多。

### 5.2 解决方案

`PageViewModel` 提供统一的弱订阅入口：

```csharp
protected static void SubscribeWeak<TSource, TEventArgs>(
    TSource source,
    string eventName,
    EventHandler<TEventArgs> handler)
    where TSource : class
    where TEventArgs : EventArgs
{
    WeakEventManager<TSource, TEventArgs>.AddHandler(source, eventName, handler);
}
```

页面 VM 这样用：

```csharp
SubscribeWeak<INotifyPropertyChanged, PropertyChangedEventArgs>(
    _plcDataCache,
    nameof(INotifyPropertyChanged.PropertyChanged),
    OnPlcDataChanged);
```

特点：

- 事件源只弱引用订阅者，页面 VM 可以正常 GC；
- 不需要手动 `-=`；
- View 的 DataContext 在显示期间强引用 VM，所以弱引用不会导致回调丢失。

### 5.3 当前使用

- `AdminViewModel` 订阅 `PlcDataCache.PropertyChanged`（报警角标）；
- `AdminViewModel` 订阅 `IAdminNavigationService.PropertyChanged`（高亮刷新）。

页面 VM 目前还没有数据订阅；后端接入后如果页面要监听缓存/服务事件，应使用 `SubscribeWeak`，不要直接 `+=`。

### 5.4 弱事件不解决什么

- **集合跨线程**：`ObservableCollection` 从后台线程 `Add` 仍然会抛异常，需要 `Dispatcher` 或 `BindingOperations.EnableCollectionSynchronization`；
- **非事件资源**：`Timer`、`CancellationTokenSource`、串口回调，需要 `INavigationAware` 或 `IDisposable` 释放。

## 6. 消息总线（WeakReferenceMessenger / EventAggregator）

### 6.1 它是什么

消息总线是发布/订阅：

```csharp
messenger.Send(new AlarmRaisedMessage(alarm));
```

发送方不知道接收方是谁；接收方注册感兴趣的消息类型。CommunityToolkit.Mvvm 提供 `WeakReferenceMessenger`，Prism 里对应 `IEventAggregator`。

### 6.2 适合做什么

- 报警产生/消除；
- 焊接完成、报告生成；
- 用户切换、权限变化；
- 主题/语言切换；
- 一个模块通知另一个模块“数据脏了”。

这些是**事件**：可能零个、一个或多个接收者，发送方不关心结果。

### 6.3 为什么不用它做页面导航

导航需要的是“唯一当前页 + 参数 + 守卫 + 返回栈 + 生命周期”，这些是**路由**职责，不是事件职责。

用消息导航的问题：

- 控制流隐形：看按钮代码只看到 `Send`，不知道谁处理、会不会有多个处理器；
- 没有单一状态源：当前页面到底是谁，要靠消息处理器推断；
- 参数、取消、返回栈都要额外协议；
- 页面带参数时消息类型会膨胀。

之前讨论过的“方法 C”（`AdminViewModel` 持有 `CurrentPage` + `NavigateToMessage`）对 9 个固定页面是可行的，但页面一多、子页面互跳一多，就会重新需要导航服务。当前项目选择保留导航服务。

### 6.4 当前状态

项目**没有**注册 `IMessenger`，也没有 `NavigateToMessage`。  
消息总线目前只是架构讨论，不是运行时代码。

如果后端需要跨模块通知，建议这样引入：

```csharp
services.AddSingleton<IMessenger>(WeakReferenceMessenger.Default);
```

```csharp
public sealed record AlarmRaisedMessage(AlarmItem Alarm);
```

但页面切换仍然走 `INavigationService` / `IAdminNavigationService`。

## 7. 一次点击的完整链路

以总览页点“查看实时数据”为例：

```text
① 用户点击 Button
      Command = OpenRealTimeDataCommand
      ↓
② AdminDashboardViewModel.OpenRealTimeData()
      _adminNavigationService.NavigateTo<AdminRealTimeDataViewModel>()
      ↓
③ AdminNavigationService
      PageFactory.GetViewModel<AdminRealTimeDataViewModel>(init)
      ↓
④ NavigationLifecycle.Leave(旧页面)
      ↓
⑤ CurrentView = AdminRealTimeDataViewModel
      ↓
⑥ AdminViewModel 收到 PropertyChanged
      CurrentPage 更新，9 个高亮属性刷新
      ↓
⑦ AdminContentHost + DataTemplate 创建 AdminRealTimeDataView
      ↓
⑧ NavigationLifecycle.Enter(新页面)
      新页面 OnNavigatedTo()，开始加载数据
      ↓
⑨ 页面 VM 用 SubscribeWeak 监听缓存/服务事件
```

## 8. 当前架构的取舍

### 保留

- 两个导航服务：窗口级 + 管理台内部级；
- `PageFactory`：统一创建页面，支持 `init`；
- `INavigationAware`：页面进入/离开时加载、取消；
- `SubscribeWeak`：防止 Transient 页面 VM 泄漏；
- `INavigationService.CurrentView` 只读，统一入口。

### 不引入

- 消息总线导航；
- 复杂的路由表/返回栈/权限守卫（当前没有需求）；
- 页面 View 注册进 DI（View 由 DataTemplate 创建）。

### 什么时候可以简化

如果以后项目收缩为：

- 只有顶部导航；
- 子页面不需要互跳；
- 不需要参数、生命周期、返回栈；

那可以删掉 `IAdminNavigationService` 和 `INavigationAware`，让 `AdminViewModel` 直接持有 `CurrentPage`，用 `PageFactory` + 回调完成 Dashboard 的两个跳转。

当前项目还在扩页面、接后端，保留导航服务更稳。

## 9. 常见坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| Transient 页面 VM `+=` 单例事件 | 切页泄漏、回调重复 | `SubscribeWeak` |
| 外部直接给 `CurrentView` 赋值 | 绕过生命周期 | 只调用 `NavigateTo` |
| 生命周期里同步等待 I/O | 切页卡顿 | 启动异步任务，离开时取消 |
| 用 `new` 创建页面 VM | 绕过 DI，依赖丢失 | `PageFactory.GetViewModel<T>` |
| 用消息总线做页面路由 | 控制流难追踪 | 导航走导航服务，消息只做事件 |
| 后台线程改 `ObservableCollection` | 跨线程异常 | `Dispatcher` / `EnableCollectionSynchronization` |
| 忘记补 `DataTemplate` | 页面空白 | 在 `ViewTemplates.xaml` 补映射 |
